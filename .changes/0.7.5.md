## 0.7.5 - 2026-10-21
### Changed
* Without urlIndex, lib.routing.getRoute(), and the getUrl template filters that call it, compose for a rule with several urls ("url": "/a/:id, /a/:id/:mode") the first url whose placeholders all receive a value, preferring among those the url that uses the most values; when no url is complete, the url that receives the most values, ties going to the first url. Before, the first url was always composed, so a call could leave a literal placeholder in the url (getRoute('logout') on "/logout/:timestamp, /logout" gave /logout/:timestamp and now gives /logout) or lose a value bound to another url. A rule whose urls carry the same placeholders, one url per language for instance, still composes its first url, and a value counts as given when it is not undefined, as for the fill itself. To keep composing the first url, pass urlIndex 0: getRoute('logout', {}, 0). (#B374)
* When a key is both in the query string of the path given to self.query() and in its data, the value in the path travels and the data's copy is not sent. For a forward route, a static param that the target url does not carry now reaches the target as written: an incoming ?k=other replaced the route's k: 'v' on a gina receiver, and a standard parser read k as 'v?k=other'. To let the caller choose that value, leave the key out of the forward route's param: the incoming query string is forwarded as it is. (#B945)
### Fixed
* `gina.validator.$forms[id].reBind()` keeps the rule set a form names with `data-gina-form-rule` when the form's id names no rule set, and so do `.bind()` and `getFormById()` on an unbound form. A bind given no rule looked the rule set up by the form's id alone, while the first bind is handed the attribute's rule, so such a form was re-bound with an empty rule set: no field was live-checked, the submit control kept its gated mark, typing no longer re-evaluated it, and the first click on a valid form was refused. Before 0.7.4 the listeners of the previous bind stayed attached across a `reBind()` and could hide the defect; since 0.7.4 detaches them, nothing re-evaluated the gate. A bind given no rule now reads `data-gina-form-rule` first, when it names a known rule set, then the id. Browser-bundled: restart the bundle and rebuild your bundles (`gina bundle:build`) to pick it up. (#B879)
* A bundle or service that had to create the run directory while it registered (a container boot whose run directory was not created beforehand, or a bundle started after the directory was removed) ran without its process title, without its SIGTERM, uncaughtException and exit handlers and without a pid file, so `bundle:stop` and `bundle:status` could not find it and a SIGTERM ended it without draining its requests. The process that creates the run directory is now registered like any other (#B852)
* A pid file was created empty and filled a moment later, so a gina command running at the same time (its start-up check prunes the run directory) could read it empty and delete it, and every other reader in that moment took the process for not running. Pid files are now written whole, through a temporary file renamed into place, and a pid file that cannot be written is reported instead of being ignored (#B857)
* A `Collection` filter on one field of an array of objects, such as `find({ 'tags[*].label': 'news' })` (the form the class documentation shows), now finds the rows whose array holds a matching element. It found no row: each element was compared as a whole, and an object never matched. The field is compared like a plain key, so a comparison (`'>= 4'`), `not null` and the constructor option `skipEval` apply to it, and a value holding `<`, `>` or `=` is a comparison there as on a plain key. An element that is not an object (a string, a number, `null`) is still compared as itself, and a dotted rest (`'reviews[*].ratings.score'`) works as before. Browser-bundled: restart the bundle and rebuild your bundles (`gina bundle:build`) to pick it up. (#B823)
* `setSearchOption()` on a `Collection` now refuses `skipEval` given to a field, in both forms (`setSearchOption('name', 'skipEval', true)` and `setSearchOption({ name: { skipEval: true } })`), with an error naming the constructor option. It was accepted, and the field then matched no row, with no error. `skipEval` is a constructor option: `new Collection(rows, { searchOptionRules: { skipEval: true } })`. A top-level `skipEval` in the object form is still accepted and has no effect. Browser-bundled: restart the bundle and rebuild your bundles (`gina bundle:build`) to pick it up. (#B824)
* `gina.validator.$forms[id].reBind(formId, rules)` binds the form with the `rules` you pass every time. It used them only after a validation on the page had found an error, because it read a global `rule` variable instead of its own argument; the validator leaked that global from an error loop that assigned an undeclared `rule`, so the first validation that found an error also overwrote any page variable named `rule`. The loop variable is declared, `reBind()` checks its own argument, and `window.rule` is no longer written. Browser-bundled: restart the bundle and rebuild your bundles (`gina bundle:build`) to pick it up. (#B880, #B802)
* `tel`, `url`, `search`, `time`, `datetime-local`, `month` and `week` fields are live-checked like `text` fields. The live check was wired only on radio, checkbox, text, hidden, password, number, date and email inputs, so typing into a required `<input type="tel">` never re-checked the form: the submit control kept its gated mark and the click on it was refused. `range` and `color` inputs are still not live-checked. Browser-bundled: restart the bundle and rebuild your bundles (`gina bundle:build`) to pick it up. (#B886)
* A field with no rule of its own that a `_case_` condition makes required (for example `company`, required only when `kind` is `pro`) is live-checked. The validator wired a live listener only on a field with rules of its own, so once the condition applied, typing into such a field never re-checked the form: the submit control kept its gated mark and the click on it was refused. A field that a `_case_` condition names is now wired when the form is bound; until its condition applies, only the whole-form check runs for it. Browser-bundled: restart the bundle and rebuild your bundles (`gina bundle:build`) to pick it up. (#B884)
* `gina.validator.$forms[id].unbind()` with no argument unbinds the handle's form. It threw "could not unbind form `undefined`" and left the form bound, because, unlike `.bind()` and `.reBind()`, it did not fall back to the handle's own form. Browser-bundled: restart the bundle and rebuild your bundles (`gina bundle:build`) to pick it up. (#B881)
* On native Windows, gina now stops at its first step with one message: run it inside WSL2 or a Docker container, with a link to the instructions. That step is the npm install, or the first `gina`, `gina-init` or `gina-container` command after an install that skipped the install scripts (a Bun install, or `npm install --ignore-scripts`). The npm install stopped with a stack trace, and the other paths crashed with unrelated errors such as `TypeError: Cannot read properties of undefined`. Native Windows is still not supported, and nothing changes on macOS, Linux, inside WSL2 or in a container. (#B888)
* When the framework is not running, a command that needs it, such as `gina bundle:start`, now tells you to start it with `$ gina start`. It used to say `$ sudo gina start`, but gina needs no elevated privileges: the framework runs as the current user, and its pid files go under the npm prefix, or to `~/.gina/run` when the prefix is not writable. `INSTALL.md`, which gave the same advice, now points to the installation guide. Nothing to restart. (#B889)
* `gina project:add` now leaves an existing `package.json` exactly as it is, as it already did for `.gitignore`. It used to rewrite it: the project name, a template description and the Node version of the machine that ran the command replaced your `name`, `description` and `engines.node`, the keys were reordered, the indent became 4 spaces, the final newline was dropped and the file was made executable. `project:restore`, which registers through `project:add`, now keeps the archived `package.json` too. A new `package.json` carries Gina's own Node floor in `engines.node` (`>=22`) instead of the running Node's version, ends with a newline, and is written at mode 0644. Nothing to restart. (#B363)
* `gina-container` now stops with exit code 1 when the project root has no `manifest.json`, and names the file and the two commands that create it: `gina project:add @<project> --path=<root>`, then `gina bundle:add <bundle> @<project> --import`. The bundle reads `manifest.json` at boot, so it never started without one: the launcher used to fall back to `bundles/<bundle>/index.js`, a path a checkout does not have, and report that path as missing, or start the bundle only for it to fail on the manifest. A `manifest.json` that is not valid JSON once its comments are ignored, or that does not list the bundle, now stops the launcher with `manifest.json cannot be used: <reason>`. An image that boots today is not affected, and there is nothing to restart. (#K8s7)
* A Couchbase entry in `connectors.json` without a `scope` now gives its entities the bundle's `NODE_SCOPE`, as documented. The connector wrote its own SDK default, `_default`, into the entry, and the model layer then took that value as the data scope: every query filtered on `_scope = $scope` ran against `_default`, so documents stamped with the bundle's scope were not found. Entries that set `scope` are not affected. Each Couchbase connector now logs its data scope at boot, and where it came from. **Documents an entry without `scope` inserted through its entities carry `_scope: "_default"` and stop matching after this fix**: stamp them with the environment's scope, or set `"scope": "_default"` on the entry to keep the old behaviour; the 0.7.4 → 0.7.5 migration notes show both. An entry without `scope` also has `NODE_SCOPE` checked when the bundle starts, as an entry's own `scope` already was: a scope name outside `^[A-Za-z0-9_./-]+$` stops the bundle with `GINA_COUCHBASE_INVALID_SCOPE`, exit code 1, where 0.7.4 gave such an entry `_default` and did not run that check. (#B893)
* A `connectors.json` entry without a `connector` field now takes its type from its key when the key is a built-in connector type (`couchbase`, `mongodb`, `mysql`, `postgresql`, `sqlite`, `redis`, `scylladb`, `duckdb` or `ai`), as `gina connector:add`, `connector:list`, the connectors schema and the connectors reference already assumed. Such an entry, which `gina connector:add <type>` has written since 0.3.7, stopped the bundle at boot with `[MODEL][<name>] No connector found`. A `connector` you set always wins, and an entry whose key names no type still needs the field. Restart the bundle. (#B900)
* A Couchbase entry whose key differs from its bucket (`"couchbase": { "database": "demo", … }`) no longer stops the boot on a project without a `models/<bucket>/entities` directory. The model layer created `models/<entry key>/entities` while the Couchbase connector reads `models/<database>/entities`, and the connector read it without checking that it exists, so the bundle aborted with `ENOENT: no such file or directory, scandir …/models/<bucket>/entities` and restarted in a loop. The connector now creates that directory first, as the MongoDB, MySQL, PostgreSQL, SQLite, ScyllaDB and DuckDB connectors already did. Restart the bundle. (#B894)
* `gina-init` no longer dials the MQ port at container start. Unlike `gina-container`, it did not apply the container logging preset, so every start printed `[MQSpeaker] Error: connect ECONNREFUSED 127.0.0.1:8125`, and in a Kubernetes pod, whose containers share `localhost`, a sidecar listening on that port would have received its log frames. It now sets `GINA_LOG_STDOUT=true` for its own process when the variable is unset, as the launcher does; its own `[gina-init]` lines do not change, and `GINA_LOG_STDOUT=false` keeps the dial. (#B892)
* `gina-container` reads `GINA_HOMEDIR`. `gina-init` writes the `~/.gina/` state there when the variable is set, but the launcher ignored it and read `HOME/.gina`, so a container that set it stopped at start with `…/.gina/projects.json not found`. The launcher now takes its home from `GINA_HOMEDIR` when it is set, and the bundle it starts gets the same value: `${GINA_HOMEDIR}` in its settings names that directory, the default certificate paths included, so an https bundle reads its certificates from `$GINA_HOMEDIR/certificates/scopes/<scope>/<host>/`. A container that does not set it is not affected. (#B895)
* The boot error of an https bundle that cannot read its certificates is spelled correctly: « You are trying to start a secured server (https) without sufficient credentials », where it read « wihtout suficient », so the troubleshooting guide's quote of it now matches the log. A log search or alert written for the old spelling no longer matches. (#B903)
* The commented `onInitialize` sample in the `index.js` that `gina bundle:add` writes now takes `self`, the gina instance, before the callback. In a bundle named `event`, `app` or `express`, the callback parameter of that name replaced the instance, so uncommenting the sample aborted the boot with « TypeError: self.getConfig is not a function ». A bundle created before keeps its `index.js`: if it is named `event`, `app` or `express` and runs that sample, move `var self = <bundle>;` above `<bundle>.onInitialize(`. (#B902)
* A `//` comment line or a `/** … */` docblock in a project's `manifest.json` no longer breaks `bundle:list`, `bundle:status`, `project:status`, `gina-container` or the bundle's boot: every reader of the file now parses it as `requireJSON()` does, as the connector CLI page already documented. Before, one comment line made `bundle:list` crash, `bundle:status` report the bundle missing from its project, `project:status` print nothing and `gina-container` refuse the project, and a bundle started another way died at boot reading `project.bundles` of `undefined`. A new global, `parseJSONWithComments(text, filename)`, parses as `requireJSON()` does but throws an Error naming the file instead of exiting the process. The CLI still drops comments when it rewrites the file, as `bundle:add` does. (#B891)
* A project file that cannot be used no longer stops the framework started by `gina start`. `gina bundle:start` now exits 1 with `<file> cannot be used: <reason>`, the reason naming the path, when the project's `manifest.json` is malformed or unreadable, or its `env.json` or `package.json` is malformed. Before, each of these stopped the framework itself: the command printed only « the framework ended this command before it reported the outcome », and every later command needed `gina start` again. A malformed `manifest.json` in another registered project is now skipped with an error line, as a missing one already was; before, it made `bundle:start` exit 0 without starting anything. When the project's `manifest.json` is missing, `bundle:start` now refuses the bundle as not registered instead of failing with a TypeError. Other commands that read the project's configuration, such as `bundle:status` and `project:status`, report a malformed or unreadable `manifest.json` or `env.json` with the same one-line message. A framework already running picks this up after `gina framework:restart`. (#B890)
* A failed `node_modules` link no longer reads as a successful start. With gina installed globally, `bundle:start`, `bundle:stop`, `bundle:restart`, `project:start`, `project:stop` and `project:restart` first run `gina framework:link-node-modules` and `gina framework:link` for the project. Those commands write their errors on their standard output and only the error output was read, so a failure gave an empty message and exit code 0: `bundle:start` reported success with nothing started. The command now exits 1 with `` `gina framework:link-node-modules @<project>` failed (exit code 1): `` followed by that command's output, which holds the reason, and `gina framework:link` reports that reason instead of a bare `Error`. A framework already running picks this up after `gina framework:restart`. (#B905)
* The model layer no longer creates an empty `models/<entry key>/entities` directory for each `connectors.json` entry. Entities are read from `models/<database>/entities` (`models/<keyspace>/entities` for a ScyllaDB entry that sets only `keyspace`), which each ORM connector creates when it is missing (none for an entry that names no `database` or `keyspace`), so an entry named differently from its database, a redis or AI entry, and an entry with no `database` (such as the in-memory SQLite session entry of the connectors reference) each left a directory nothing reads, and a debug line named that path. The bundle's `models/` directory is still created at boot. A directory an earlier version left behind can be deleted. Restart the bundle. (#B901)
* A ScyllaDB entry that names its keyspace with `keyspace` alone, as the ScyllaDB guide configures it, now loads its entities from `models/<keyspace>/entities` and its CQL methods from `models/<keyspace>/cql`. The model layer passed the connector the entry's `database` only, so such an entry booted with none of its entities, and the connector created an empty `models/undefined/entities` directory. An entry that sets `database`, as `gina connector:add --database` writes it, keeps its directory, also when it sets `keyspace` too. A ScyllaDB session entry that sets only `keyspace` now gets `models/<keyspace>/entities` instead of `models/undefined/entities`; when an ORM entry uses the same keyspace, the session entry's model also carries its entity classes, bound to the session connection. An empty `models/undefined/entities` directory left by such an entry can be deleted. Restart the bundle. (#B909)
* A `connectors.json` entry that names neither `database` nor `keyspace`, such as the SQLite session, job and kv store entries the guides show, no longer leaves an empty `models/undefined/entities` directory: each ORM connector named its model directory after the entry's `database`, and now creates and reads none for such an entry. A SQLite entry that sets neither `file` nor `database`, such as the session entry of the going-to-production tutorial, also made the model layer open a database file `undefined.sqlite` in the gina home (`~/.gina` by default); it now gets an in-process (`:memory:`) database. The session, job and kv stores open their own file and are unchanged. A `models/undefined/entities` directory and an `undefined.sqlite` file left by an earlier version can be deleted, but data stored through the connection of an entry with neither `file` nor `database` is in that file: set the entry's `file` to it before upgrading. Restart the bundle. (#B907)
* A DuckDB `connectors.json` entry that names neither `file` nor `database` now stops the boot: the bundle exits with code 1, and its log names the two keys the entry is missing. It used to open a database file `undefined.duckdb` in the gina home (`~/.gina` by default), or `.duckdb` for an entry with both keys set to empty strings, and the boot went on. Set `database` (it names the model directory and the default file `~/.gina/<database>.duckdb`) or `file` (a path, or `:memory:`); an empty string counts as absent. Data stored through such an entry by an earlier version is in that file: set the entry's `file` to it before upgrading. Restart the bundle. (#B911)
* `gina-init`, `gina-container` and the install step (`npm install gina`) now write the `~/.gina` files they update whole. `gina-init` rewrote `projects.json`, `ports.json`, `ports.reverse.json` and its `settings.json` in place, `gina-container` rewrote `main.json` in place when it updated `def_framework`, and the install step did the same when it updated `def_framework`, the frameworks list or `def_global_mode`; a `gina` command or a bundle reading the file at that moment, such as another container sharing `~/.gina`, could find it empty or cut short and stop. Each file is now written to a temporary file in the same directory and renamed into place, as the other `~/.gina` writes already were, and an existing file keeps its permissions. Nothing to change: the temporary files exist only while a file is written. (#B687)
* On a rule set with no `$` reference, each validation check works on its own copy of the rules. It wrote what it decided into the form's stored rules, and nothing put them back: once a `_case_` condition had applied, its rules stayed applied after the driving field changed back, so a valid form kept its submit control gated and refused the click, and forms bound to the same rule set could gate each other; and a checkbox whose rule says `isRequired: false` and that was unticked when a check ran stayed out of the posted data after the user ticked it. A rule set with a `$` reference already worked on a copy. Browser-bundled: restart the bundle and rebuild your bundles (`gina bundle:build`) to pick it up. (#B885, #B913)
* A radio or checkbox group that only a `_case_` condition makes required is checked from the first submit once the condition applies. The validator collects an unchecked group only when the group's own rule says `isRequired`, so a check refused the group only after an earlier check had written the condition's rule into the form's stored rules: with live checking off, or a radio button as the driving field, the first submit went out without the group, and with a `$` reference in the rule set every submit did. The matching condition now enters the unchecked group as an empty value, and the required check refuses the submit until a member is picked. Browser-bundled: restart the bundle and rebuild your bundles (`gina bundle:build`) to pick it up. (#B914)
* After a change on a `<select>`, the validator re-checks the whole form with the form's own rules. It used the rule registry, keyed by rule-set name, where no field has a rule, so a radio group whose rule says `isRequired: true` and that nobody had picked was not seen: the submit control lost its gated mark, although a click on it still sent nothing. Browser-bundled: restart the bundle and rebuild your bundles (`gina bundle:build`) to pick it up. (#B915)
* An unticked checkbox whose rule declares `isBoolean` together with `"isRequired": false` was left out of the posted data; it now posts `false`, as every other unticked boolean checkbox already did. A handler that tested for the field's presence now receives `false`. On an edit form whose server keeps the stored value of a field the request leaves out, unticking such a box used to change nothing, so a stored `true` stayed `true`; it now posts `false`, and the stored value becomes `false`. A disabled checkbox is still left out, and so is an unticked checkbox that carries a value other than `true` or `false` with no `isBoolean` rule. Browser-bundled: restart the bundle and rebuild your bundles (`gina bundle:build`) to pick it up. (#B916)
* A `~/.gina/projects.json`, `ports.json` or `ports.reverse.json` that cannot be read or parsed no longer stops the framework started by `gina start`. `gina bundle:start` now exits 1 with `<file> cannot be used: <reason>`, the reason naming the path; before, the command printed only « the framework ended this command before it reported the outcome », and every later command needed `gina start` again. A `~/.gina/main.json` that cannot be read or parsed stopped only `bundle:start`, with a long message; it now gets the same one-line refusal, after a warning that `def_framework` could not be synced. `bundle:status`, `bundle:list`, `project:status` and `service:list` report a `ports.json` or `ports.reverse.json` that cannot be read or parsed in that one line too: their documentation said a malformed `ports.reverse.json` was tolerated, but these commands exited 1 with a long message. A missing `ports.reverse.json` is still recreated empty and shown as `(no port)`. A framework already running picks this up after `gina framework:restart`. (#B906)
* Each condition of a `_case_` block is matched against the value of its driving field. Once a condition had matched, the validator compared the next conditions of the same block with the value of a field the matched condition names (as a boolean when that field's own rule says `isBoolean`), so a later condition whose `case` equalled that value applied although the driving field did not match it: a field it requires refused the submit, and a field it excludes was left out of the posted data. A later condition that matches the driving field still applies. Browser-bundled: restart the bundle and rebuild your bundles (`gina bundle:build`) to pick it up. (#B920)
* A `_case_` condition whose `case` is written `/pattern/flags` (the form the 0.3.15 migration notes show with `"case": "/^individual$/"`) is tested as a regular expression against the value of its driving field. The validator compared that string with the value, so it did not match: when the condition's `_case_` block was the only or the last one of the rule set, the condition applied nothing, neither the requirements nor the excludes it declares; when another `_case_` block followed it, a later check applied its rules to the fields the form collects, but a radio or checkbox group it requires was not refused. The pattern is read as written, so `[ab]` is a character class. A value that starts and ends with a slash and is meant literally can be put in an Array (`["/fr/"]`), and a pattern the browser does not accept is still compared as a value, with a console warning. Browser-bundled: restart the bundle and rebuild your bundles (`gina bundle:build`) to pick it up. (#B918)
* A field carrying `data-gina-form-element-group="<id>"` now follows only the radio or checkbox it names: it is enabled, and sent, while that control is checked. Every radio, at page load and on every click, disabled every such field of the form and enabled again only its own, so a click on another radio left a checked master's fields out of the posted data, a checkbox master's fields too; at page load the fields of a master checked in the HTML were left out unless it was the last radio of the form; and a field whose group names no element was left out as soon as the form held a radio. A field now changes only with a master it names, and a field whose group names no element of its form is left as the HTML renders it. A checkbox that is disabled now counts as unticked for the fields that name it: a field naming a master and a checkbox grouped under it stays out of the data once the master is switched off, even with the checkbox still ticked, and a field naming a checkbox grouped under another checkbox is no longer sent while the outer one is unticked. Browser-bundled: restart the bundle and re-bake your bundles (#B919).
* The `swig.package` setting in the settings.json schema now lists `@rhinostone/swig-jinja2` and `@rhinostone/swig-django` beside `@rhinostone/swig` and `@rhinostone/swig-twig`, so editors no longer mark the Jinja2 and Django frontends as invalid. The schema also says that a value other than the default needs `swig.useProject: true` and a 2.x version of that package installed in the project, because only `@rhinostone/swig` has a framework copy to fall back to (#B924).
* When `requireJSON()` cannot parse a file, its message quotes the file around the error and marks the error with `--(ERROR !)--`. The quote ended at a fixed character, so for an error past the first 500 characters it stopped short of the error: the marker never showed, and a long file was printed almost whole. The quote now runs from 200 characters before the error to 300 after it. (#B917)
* A field carrying `data-gina-form-element-group` now follows only the masters whose ids its group lists. Each id was looked for anywhere in the list, so an id found inside a longer one matched too: with masters `opt` and `opt-2`, the radio `opt` drove the fields of `opt-2`, a checkbox `item-1` those of `item-10`, and a master checked in the HTML could find its fields disabled at page load. Each id is now matched as a whole entry of the space-separated list, so a group must list each master's id itself: an entry that only contains it, such as `opt-2` written to follow `opt`, or ids joined by a comma, no longer follows that master. Browser-bundled: restart the bundle and re-bake your bundles (#B923).
* The framework's helpers load in a fixed order whatever order the file system lists them in. Node lists a directory sorted and Bun as the file system does; four helpers load the logger, which loads three of them back while it loads, so under Bun a process that loaded the helpers before the logger could fail with `TypeError: require(...) is not a function` when `path.js` or `json` came first. The entries are now sorted before they load, the order node has always used. Server-side: restart the framework and your bundles (#B927).
* A radio or checkbox master whose id holds a regular-expression character (`+`, `*`, `?`, `$`, `^`, `(`, `)`, `{`, `}`, `|` or `\`) now drives the fields whose `data-gina-form-element-group` names it. The id was escaped for `- _ @ # . [ ]` only and read as a pattern otherwise, so `plan+1` found `plan1`, `opt*2` found `op2` and `opt2`, `a$b` found nothing, and an id holding `(` stopped the form from binding. Every regular-expression character of the id is now escaped at the five places a group is matched, and the second expression `updateReletadItems` built from a checkbox's own group as written, whose result never mattered, is gone. Browser-bundled: restart the bundle and re-bake your bundles (#B929).
* An unticked checkbox that carries a value and whose own rule says `"isRequired": true` is now refused: `isRequired` on such a checkbox means it must be ticked, as it does for a radio group (several boxes under one name: at least one ticked; boxes with distinct names: each one). Before, no rule judged it, so the form posted without the box and the required check never fired, in the browser or on the server. A boolean checkbox (no `value`, a `true`/`false` value, or an `isBoolean` rule) still posts its live state, a required `false` still passes, a disabled box is still left out, and an unticked box with no rule or with `"isRequired": false` is still absent from the posted data. Browser-bundled: restart the bundle and rebuild your bundles (`gina bundle:build`) to pick it up. (#B926)
* A key of a `_case_` condition's `rules` written as a regular expression (`"/^item[/": { "isRequired": true }`) now applies to every field it matches, wherever its `_case_` block sits in the rule set and whatever the shape of its `case`. ### Security
* A `:placeholder` in a route's `param.file` that is also a URL segment now takes the URL value. A query or body value of the same name replaced the segment after it had passed the route's `requirements`, so a request could render another template under the bundle template root: the residual stated in GHSA-3vmh-634f-vwm3, now closed. A placeholder the URL does not carry is still filled from the query or body, as before, and a query key folded in by its own requirement still selects its template. Restart your bundles (#B877).
* A route's `param.path` and `param.namespace` no longer take an escaping value without the router's path-traversal check. The router wrote a URL segment, or a query key folded in by its own requirement, into those two fields before that check ran, so a value holding a `..` segment or starting with a separator was not refused there; the template renderers refused such a template path (500). The router now refuses it first (500). A redirect route that takes `param.path` from a query value starting with `/` is refused too: since 0.7.4 when the key has no requirement, and now also when it has one. Write the target in `param.path`, or call `self.redirect()` from an action. The router claim in GHSA-3vmh-634f-vwm3 now holds. Restart your bundles (#B883).
* Gina now requires `@rhinostone/swig` `^2.8.3` in both manifests. Up to 2.8.2, swig wrote the including template's filename into the compiled template without escaping it: a double quote in a template's path made a template that includes, imports or extends another fail to compile, and an async `import`, `from` or `extends` wrote a backslash in the path as it was, which corrupted it. 2.8.3 escapes the filename wherever it is written (advisory GHSA-q89c-947c-m7xr). Upgrading gina installs 2.8.3 or later (a project copy loaded through `swig.useProject` keeps its own version, so update it there); restart the bundle. (#B942)
