## 0.7.4 - 2026-10-15
### Changed
* A route's `cache` field sets `Cache-Control: <visibility>, max-age=<ttl>` on its responses only while the bundle's server cache is on (`server.cache.enable`) and the request is a GET, the same gate as the cache write. Until now the header went out whatever the switch, in development with the cache off and on routes whose server-side cache was switched off, so a browser could reuse a page or a JSON answer for the route's whole `ttl` while nothing on the server cached it. With the cache off, responses carry no `Cache-Control` from the route (#B744).
* The SQLite driver seam takes the `node:sqlite` class as `Database` where the runtime exports it and as `DatabaseSync` everywhere else. Node.js 26.11.0 renamed the class to `Database` and kept `DatabaseSync` as a deprecated alias (DEP0210). The framework reached the class through the old name only, so it would have stopped resolving a driver on a runtime that drops the alias. Nothing changes on a current runtime: Node.js 26.11 and later export one class under both names, and older Node.js and Bun export `DatabaseSync` only. The SQLite connector, the session store, the async-job store, the key-value store, the storage metadata store and the framework state store all resolve their driver through this seam (#B829).
### Deprecated
* In `settings.json`, the top-level `cache` block carries the render cache's default backend (`type`, `store`, `name`); its switch and bundle-wide defaults (`enable`, `path`, `ttl`, `sliding`, `maxAge`, `maxEntries`) have always been read from `server.cache` only and were silently ignored in the top-level block. A bundle now logs a boot warning for each such key found there, naming `server.cache`, and the settings schema marks them deprecated at that place (#B744).
### Fixed
* `gina start --inspect-gina` now returns the framework's own exit code when the framework ends before it is ready: the code it exited with, or 128 + the signal number when a signal stopped it (137 for `SIGKILL`). It returned 1 with « exit code 0 », the code of the debug launcher, whatever had happened to the framework (#B764).
* `gina framework:restart` now exits with `gina start`'s code when the framework does not start again, after relaying the start's output and one line naming the failure. It returned 0, with no framework running, when the failed start had already written its pid file, and otherwise ended with an uncaught error and exit 1, the start's own code lost (#B780).
* `gina framework:status` now lists a framework running on Bun whose pid file is missing, and writes its pid file back, and `gina stop` now stops it. Both looked for the framework by its `gina-v<version>` process title, which Bun does not show to `ps`, so status read « Gina is not running » and `gina stop` exited 0 leaving the framework running. Both now also read the framework's own `procs.json` record, and act on it only while `ps` shows that pid running as the framework. A framework on Node whose pid file is missing is now sent `SIGTERM`, as one with a pid file is, instead of `SIGKILL`, so it exits cleanly and removes its own record (#B763).
* The live check of a `<select>` now displays the select's error from the whole-form pass. After a change, the validator checks the select alone, then the whole form; the second pass read the global `event` instead of the select, and during that pass the event belongs to the form, so it looked the error up under the form's name and displayed nothing. An error only the whole-form pass finds, such as a rule comparing the select with another field, was not shown by the live check. Browser-bundled: rebuild bundles to pick it up (#B781).
* `gina image:run <image>` without `--name` now leaves the container name to podman, as documented. The image reference was taken as the container name: a usual `repo:tag` reference was refused with « invalid --name », so the command failed in its plain form, and a reference that is also a valid container name, such as `demo`, named the container after the image and reported that name. `--name=<name>` still names the container (#B779).
* The `fs` cache strategy reads its entries back after a restart from the directory it writes to. A bundle setting `server.cache.path` to its own directory wrote every entry there, but a restarted process looked for them under the project's `cache` directory, so the first request of each cached URL rendered again instead of answering from disk; `gina cache:clear` reclaimed orphaned entries under the same default directory only. Both now follow the bundle's `server.cache.path` (`cache:clear` resolves it for the project's default env from `settings.server.cache.<env>.json`, `settings.json` and the project `env.json`) (#B785).
* A per-environment settings file with no section, `settings.<env>.json`, is now merged into the bundle's settings at the top level and wins over `settings.json`, as `settings.<section>.<env>.json` does for its section. It used to be nested under a `<env>` key of the settings instead, so nothing in it took effect (#B784).
* A staged file-upload form that declares `[preview][location|uri|width|height]` sub-field inputs now leaves each one empty when the replacement file's staging response does not carry that preview value, instead of posting the replaced file's. On an edit form the declared preview inputs had kept the previous file's metadata and were submitted with the new file; a partial preview (some sub-fields present, others not) left the omitted ones stale the same way. The documented contract — a declared sub-field the response does not carry is left empty — now holds for both the no-preview and partial-preview cases, and undeclared forms are unchanged (#B791).
* A controller action that answers an error with `self.throwError(err)`, where `err.fallback` names a redirect target, now answers an XHR request that carries params (a form body or a query) or comes from a popin: the request receives the `isXhrRedirect` JSON pointing at the fallback. That JSON used to be dropped, so such a request was never answered and its client waited until its own timeout, a `self.query` call made from another bundle on behalf of an XHR request included. Non-XHR requests, and XHR requests without params, were unaffected and still receive the 301 or 303 (#B783).
* `self.redirect()` to an absolute URL whose host has no dot (`http://localhost:<port>/…`, a single-label host such as a container service name, or a bracketed IPv6 address) now redirects to it. Such a URL used to be taken for a route name and answered with a 404 naming the current URL; a `throwError()` fallback given as a route object failed the same way on a bundle served from `localhost`, because the route object's URL is such an absolute URL. URLs on dotted hosts, route names and relative paths are unchanged (#B794).
* `self.throwError(err)` with a single error object now keeps the object's `message` and its `ref`, as the `(code, err)` and `(res, code, err)` forms already did. A plain object kept only its `status` and `error`: its `message` reached neither the JSON body, nor the built-in error page, nor the incident log line, and a `ref` on a plain object or on an `Error` was replaced with a fresh one. This hit the relay between bundles: `self.query()` hands its callback the upstream's error body as a plain object, so `return self.throwError(err)` answered without the upstream's sentence, under a ref that matched no upstream log line. A ref is still kept only when relay-safe, and `error` is unchanged. A fast lane route's `ctx.error(err)` answers the same way (#B518).
* `gina stop` now signals a framework only after `ps` shows that the pid it read is still running as that framework, and it reads and removes only its own version's pid file. It used to remove the pid file of every framework version in the run directory before choosing the one to stop, so stopping one version deregistered the others running beside it, and `gina reset`, which checks those pid files for running frameworks, could then miss them. It then sent `SIGTERM` to the pid that `procs.json` records for the version whenever a pid file held the same pid, whatever process that pid now was (a reused pid, or one recorded in another container's pid namespace when the run directory is shared), sent `SIGCONT` to the record's `fakeDaemonPid`, which names the `gina` wrapper that exits once the framework is ready, and printed « has been stopped » whether or not it had signalled anything. Where `ps` cannot identify a process (Windows, an image without `ps`), the pid that the pid file and the record both name is still signalled (#B782).
* A `:placeholder` in a route's `param.path`, `param.title` or `param.namespace` now takes its value as written, on a matched request and through `getRoute()`. These fields took the value through a string replacement, so `$` sequences in it were expanded as replacement patterns: a request to `/user/$%60` on a `/user/:id` route gave `"title": "User :id"` the value `User User `, and `$&`, `$'` and `$$` inserted the placeholder, the text after it, or a single `$`. `getRoute()` also dropped the `/` that follows such a placeholder in those three fields: `"path": "/users/:id/edit"` with `id: 42` gave `/users/42edit`, and now gives `/users/42/edit`. The URL and `param.file` already took the value as written (#B688).
* `filter(fn)` on a `Collection`, or on an array one of its query methods returns (`find()`, `orderBy()`, `limit()`, `notIn()`, and so on), now filters like `Array.prototype.filter`: the callback gets `(row, index, array)`, a second argument is its `this`, and the result keeps the methods of a `find()` result, so `.toRaw()` and the chain still work. Those arrays carry their own `filter`, a field projection, and it read a function as a field name: `rows.filter(fn)` returned an empty array with no error. A field name or a list of field names still projects each row (#B517).
* Calling reBind() on a form no longer stacks the validator's listeners on the form, its fields and its submit trigger: unbindForm detached nothing (its form-level removals passed the validator record, which has no removeEventListener, and its per-element removals passed no handler), so every re-bind attached one more copy of each. On Safari, one keystroke in an autocomplete="off" field inserted one character per re-bind; after a re-bind a consumer's .on('submit') handler was bypassed (its registry key had been deleted, so the validator sent the form itself) and re-registering .on() attached a second handler. The binding now records every listener it attaches and unbindForm detaches exactly those, by reference. Handlers registered with .on() and the declarative data-gina-form-event-on-* hooks survive a reBind(); destroy() removes them too, unless the form has already left the document (a popin replacing or clearing its content), where they die with the element so an answer still on its way reaches them. A form bound again after destroy() claims its submit trigger again. A stray window listener registered per live-checked field is gone. The registry-restoring workaround some applications carried around reBind() is no longer needed (#B585)
* An `async` route middleware whose returned promise rejected (an error thrown after an `await`, or thrown by a later middleware it handed over to through `done`) left its request unanswered until the client or a proxy timed out, and the rejection reached the process unhandled. Such a request is now answered with a 500 that names the middleware, carrying an `#ERRREF` correlation reference with the full detail on the paired server log line, as a rejected controller action or reserved hook already was (#B812).
* The `getUrl` template filter degrades instead of throwing in a render context that has no request, or no bundle configuration (#B516). On both the swig and the nunjucks engine the filter sent every rule form (`'home' | getUrl`, `'home@admin' | getUrl`) and every path given a bundle as its base through a branch that read the request's headers unguarded, and it read the context's bundle configuration unguarded before that. A context built outside a request - a mail or scheduled-task renderer that calls the filter factory itself - threw `TypeError: Cannot read properties of undefined (reading 'headers')`, and a context with no bundle configuration threw on every form, a plain path included. Such a render now gets its URL from the target bundle's configured hostname, or from the worker's proxy host when one is known, as a `getRoute()` call with no request in scope does; it never carries `:NaN` or `scheme://undefined`. Two cases still throw, with a named `Error`: a base naming an unknown bundle when the context has no `throwError`, and a render for which no bundle configuration resolves. A request render is unchanged. Server-side only: restart the bundle.
* An async job runs with no render context (#B811). The template filters (`getUrl`, `getWebroot`, `t`, `tIcu`) look for their context in the render store first, and the 0.6.31 fix detached a job from the request store only: the job kept the render store of the async chain that started it. A job created while a render context was active ran with that context, the `req` and `res` of its request included. A job that had waited for a worker slot ran with the render context of the job that freed the slot, whichever request had created either, and so did each of its retries. A template filter called in such a job resolved that request's context, so `getUrl` built its absolute URLs from that request's host, even when the job had passed a context of its own to the filter factory. A job now runs with no render store for its whole lifecycle, and a filter it calls resolves as in a render made outside a request. Affected: 0.4.6 through 0.7.3. Server-side only: restart the bundle.
* A `Collection` search that carries a search option (`setSearchOption(field, 'isCaseSensitive', false)`) now matches the filter value as text. The value was spliced unescaped into the rule's pattern: a value holding an unbalanced parenthesis threw a `SyntaxError` out of `find()` / `findOne()`, a dot matched any character (so `a.b` also selected `axb`, and `update()` / `delete()` then acted on both rows), and a `$&`-style sequence in a value was expanded. A pattern character in a value now means itself, and a value without one matches exactly as before. A rule template passed to the constructor (`searchOptionRules`) still applies: only the value is escaped. A value holding `<`, `>` or `=` is still a comparison unless `skipEval` is set (#B818).
* A `Collection` search option now works for every search on an instance, not only the first. The first value compared under an option was written back onto the rule table, so every later option search on that instance matched the first value (`find({ name: 'alice' })` then `find({ name: 'bob' })` returned Alice twice), one search over two option fields matched nothing, and a rule table passed to the constructor carried the first value to every instance built from the same options object. The rule table is no longer written (#B819).
* The object form of a `Collection` search option, `setSearchOption({ field: { isCaseSensitive: false } })`, now works. It tested each top-level key, a field name, against the rule table, so the documented shape threw `undefined is not an allowed searchOption !` and only the three-argument form was usable. Each field's rule names are now checked (an unknown rule is refused by name, a field entry that is not an object of rules is refused by field), `'true'` / `'false'` are read as booleans like the three-argument form, and the options are copied: the caller's object is neither kept nor changed (#B820).
* A `Collection` filter whose dotted key holds `(`, `)` or `[` in its last segment (`find({ 'address.ci(ty': 'Paris' })`, also in the `[*]` form) no longer throws a `SyntaxError` out of the search: it matches nothing, like any other dotted key that is not a property path. A regular expression was built from the key and never read (#B821).
* A bundle that renders through a custom async swig template loader (`settings.template.swig.loader`) renders its pages again: from 0.6.30 to 0.7.3 every page render of such a bundle answered 500, with `TypeError: swigMod.Swig is not a constructor` in the server log. The async render path builds an engine of its own from the swig module, and it was handed the bundle's own engine instance instead, which has no `Swig` constructor (#B808).
* `Collection.update()` writes each matched row back over the row it came from. With rows that have no `id`, every merged row went over the first one: a row was lost, another appeared twice and the rest were not updated, with no error. A single matched row did the same once an earlier `update()` or `toRaw()` had run on the same collection, and so did an empty filter, rows sharing an `id`, and an explicit `'id'` key on rows without one. Rows found through another collection were not written at all; they are now written by their `id` (#B822).
* A logged object can no longer make a log call throw. The levelled logger counted the keys of a logged object through the `count()` helper, an ordinary property lookup, so an object with an own `count` key (a parsed body `{"count": 5}`) made the call throw `obj.count is not a function` in the caller. Both writers tested `instanceof Object`, which is false for a null-prototype object (the result of `querystring.parse()`, `Object.create(null)`): such an object fell into a string path, and coercing it there threw `Cannot convert object to primitive value`. An array element `{"toString": "x"}` and a Symbol made the coercion of a value throw too. Keys are now counted with `Object.keys`, a null-prototype object is written like any other object, a value that cannot be coerced is written as its type tag (`[object Object]`), and a Symbol is written with `String()`. An object with an own `hasOwnProperty` key is now written with its commas. Every other value is written exactly as before. Pickup: a bundle restart; the logger is not in the browser bundle (#B832).
* `Collection.find()` lists a row once when it matches several of the filter objects it is given. Two or more filter objects are an OR clause, and a row matching two of them was listed twice (three of them, three times): the result held the same row object more than once, `limit(n)` on it dropped a real row, and a chained `update()` met the row twice. The result now holds each matching row once, in collection order. A call whose filters cannot match the same row (two values of one key, for example) returns what it returned before (#B827).
* `Collection.delete()` and `notIn()` take the rows they found out as themselves. Given a filter, they located each found row by a key read from the first one, the internal `_uuid` or else `id`: after `toRaw()` or `update()` had stripped that `_uuid`, rows with no `id` threw `No comparison key defined !`, and rows sharing an `id` lost the first row holding it instead of the row found, with no error. The no-key form, `delete(filter, false)`, threw the same way on rows with no `id` and removed nothing for a dotted key. When no key is named and the rows found are rows of the collection or of the chained result searched, each is now removed at its own place. A named key, and rows passed in from elsewhere, are compared by key as before (#B826).
* An exception thrown while the framework parses the data of a request is answered as a `500` instead of ending the bundle. The query of a `GET`, `HEAD` or `DELETE` request, the end of the `PUT` body branch and the hand-off to the dispatch that follows on the same stack ran with no `try`, so an exception raised there reached the process as an `uncaughtException` and the bundle exited (code 143): the path three earlier defects took, each fixed at its cause (#B546, #B591, #B792). The call that runs this parse is now guarded, as the `POST`, `PUT` and `PATCH` body branches already were: the request is answered through `throwError()` with a `500` (JSON for an XHR or API request, the bundle's own error page for an HTML one) and an incident ref, and one error-level log line pairs that ref with the stack. No input is known to raise such an exception today: the guard is a net under the parse, and what it catches is logged so that its cause is fixed. Both engines. A `multipart/form-data` request never runs that call and is not covered by it. Restart the bundle; nothing to re-bake (#B793).
* A throw inside one of the listeners that parse a `multipart/form-data` request is answered as a `500` instead of ending the bundle. The `field`, `file` and `finish` listeners ran with no `try`, so an exception raised in one reached the process as an `uncaughtException` and the bundle exited (code 143) on Node.js 22. On Node.js 24 and later the outcome depended on the listener: an exception in the `field` listener was forwarded to the parser's error listener, which answered a misleading `400` for a body that was not malformed; one in the `file` listener, raised where the file's write stream is created, was answered that `400` and the bundle then exited; one in the `finish` listener got no answer and the bundle exited. The listeners are now wrapped — `busboy.on` is overridden in place for those three registrations and given back before the request is piped, so their registration is unchanged — and a throw is answered through `throwError()` with the same `500` `Could not evaluate <METHOD> request data.` on every supported Node version (JSON for an XHR or API request, the bundle's own error page for an HTML one), with an incident ref and one error-level log line that pairs the ref with the stack. A genuinely malformed `multipart/form-data` body still answers `400`. The callbacks nested inside a file part run under the same wrapper (#B844): the `error` and `finish` handlers of the temporary file's write stream, its close callback, the `end` handler of the file stream and the callback of the `autoTmpCleanupTimeout` timer. They ran outside it, so an exception raised in one of them ended the bundle on Node.js 22, 24, 25 and 26; a request that carries a file is handed to its action from the close callback, so the same exception that was answered `500` for a body without a file ended the bundle for a body with one. Such an exception is now answered with the same `500`, or logged with its stack when the request is already answered (a write error answers its own `500`; the cleanup timer runs after the answer). The guard's own log line writes the exception message with its control characters as visible escapes. No input is known to raise such an exception today: the guard is a net, the companion of the request-data parse guard, and what it catches is logged so that its cause is fixed. Both engines. Restart the bundle; nothing to re-bake (#B843).
* An HTML request whose custom error page could not be dispatched is answered with the built-in error page instead of ending the bundle. When an error reaches `throwError()` on an HTML request and the bundle has an error page for its status (`templates/html/errors/`), the framework dispatches that page through the router. When building the error-page controller raised, the router's catch called `throwError()` again for the same request, which dispatched the page again: the cycle repeated until the call stack overflowed, the request got no answer and the bundle exited (code 143) on Node.js 22, 24, 25 and 26. The guard that keeps an error page from rendering twice did not apply: it acts once the page renders, after that point. The error page is now dispatched at most once per request: the dispatch marks the request, and a later `throwError()` call for a marked request answers with the built-in page, which shows the status and the incident ref of that call; its error-level log line pairs the ref with the cause of the failed dispatch, and the line of the first error carries the same request id. A request whose error-page dispatch does not raise gets the custom page as before. No input is known to make that dispatch raise today: it was measured with test doubles over the request-data parse. Both engines. Restart the bundle; nothing to re-bake (#B842).
* A request field named `hasOwnProperty` reaches the action like any other field. gina's `count()` helper on `Object.prototype` tested each key with `this.hasOwnProperty(key)`, an ordinary property lookup: on an object with its own `hasOwnProperty` key that is not a function, such as a parsed request carrying a field of that name, the call threw and the helper returned 0, with no error. The request pipeline decides from that count whether to hand the parsed data over, so with such a field the action received an empty `req.get` on GET and HEAD and an empty `req.delete` on DELETE, and on POST and PATCH `req.body` stayed the raw body string (`req.post` and `req.patch` were complete). The helper now tests each key with the built-in `Object.prototype.hasOwnProperty`: such an object is counted like any other, and so is an object with no prototype (`Object.create(null)`, `querystring.parse()`) reached through `Object.prototype.count.call()`; every other count is unchanged. A `req.post.count()` in your own code counts that field too now. The same applies to `functionCount()`, which threw on both kinds of object, and to the validator's `is` rule, which answered « could not evaluate » when the data it validated held a field named `hasOwnProperty`. Restart the bundle and re-bake each bundle: the browser bundle carries its own copy of the helper and of the validator (#B837).
* A worker child no longer takes over its bundle's pid file. A worker is a child process whose entry is named `child.js` or `child-*.js` and that is loaded with `--argv-filename`: the framework imports its parent bundle's context and registers it under the bundle's name. It registered with a pid file, so it wrote its own pid into `<bundle>@<project>.pid` and removed the file when it exited. While a worker was running, `bundle:stop` signalled the worker instead of the bundle, and `bundle:restart` exited 0 while the old bundle kept serving: the new start failed on the port the old process still held, and `bundle:start` reported that as a success (#B851, fixed in the same release). Measured on a booted bundle and in an isolated daemon. A worker now registers without a pid file. Its `gina: <bundle>@<project>` title and its signal handlers are unchanged. The framework sets `process.isMinion` in it, so its exit never removes the bundle's mount link. Pickup: no bundle restart, a worker spawned after the update registers the new way. A worker started before the update keeps the old registration until it exits: while it runs, the first `bundle:restart` ends only that worker and leaves the old bundle serving, and a second `bundle:restart` restarts the bundle (measured in an isolated daemon); that first restart now exits 1 instead of 0 (#B851, measured with a pid file naming another process). A bundle whose pid file an older worker already removed gets it back the next time the bundle starts (#B850)
* `req.delete` is a plain object with Express 4 and a `querystring`-based query parser. With Express 4 and `app.set('query parser', 'simple')`, or any query parser returning an object without a prototype, the DELETE branch handed that object over as `req.delete`, so on every DELETE to a path after the first `req.delete.count()` and `req.delete.hasOwnProperty()` were not functions. Measured with express 4.22.3. The DELETE branch now hands over a plain object holding the query's own fields. Express 4's default parser (`extended`) and Express 5 already gave a plain object. Server-side only: restart the bundle, nothing to re-bake (#B847)
* A `gina bundle:start` that the framework refuses before it starts anything no longer stops the framework. `bundle:start` runs inside the framework's own process, and a refusal such as an unregistered `@<project>` or an invalid bundle name ended that process (exit code 1) while the command exited 0, so every later command found no framework running (measured in an isolated daemon). The refusal now ends only that command, with exit code 1, and the framework keeps running; an error thrown while the framework prepares the command is handled the same way. Pickup: restart the framework (`gina framework:restart`) (#B855)
* `gina bundle:start` now exits with a code that says whether the bundle started. It exited 0 for every outcome: a crash during startup, a port another program holds, the startup timeout, a refusal and a bundle already running (measured in an isolated daemon). It now exits 0 when the bundle listens, or when it already runs (its pid file names a running process titled `gina: <bundle>@<project>`); 1 when another program holds the port, with a line that names the port and, outside Windows, a command that finds the holder; the bundle's own exit code when it stops before it is ready (1 when that code is 0), or 128 plus the signal number; 1 on the startup timeout and on a refusal, such as a bundle the project does not declare or a `scopes` allow-list; and for `bundle:start @<project>`, 1 when any bundle failed. A bundle that already runs is not started again: the command prints `[ <bundle>@<project> ] is already running with PID [ <pid> ]`. A bundle that exits 0 before it is ready, and one whose process cannot be spawned, are reported at once, where the command waited for the 64 s timeout. The command no longer stops early when node cannot bind the debugger port (`--inspect`): the bundle starts without the inspector, and the command waits for it and reports it. `project:start` and `bundle:restart`, which run `bundle:start`, exit 1 when it exits non-zero, whatever its code. Pickup: restart the framework (`gina framework:restart`); until then the command behaves as before (#B851)
* `gina bundle:restart` now exits 1 when the bundle did not restart. Its start step exits non-zero on a failed start (#B851), and a start that exits 0 must leave a running bundle that is not the process that ran before the stop: a stop that missed the bundle used to end with the old process still serving and exit code 0 (measured with a pid file naming another process, the shape of #B850). On a failure the command prints what its stop and start steps said. `bundle:restart @<project>` exits 1 when any bundle failed, where only the last bundle's outcome decided it (measured: the first bundle failed, the last restarted, exit 0). `project:restart`, which runs `bundle:restart @<project>`, exits 1 in the same cases. Pickup: the next command (#B853)
* A `gina bundle:start` on a bundle that is already running no longer deletes that bundle's pid file. The second start spawned a new process that wrote its own pid into `<bundle>@<project>.pid`, could not bind the port, and removed the file as it exited, so `bundle:status` read the running bundle as stopped and `bundle:stop` found it only by its process title (measured in an isolated daemon, for `bundle:start <bundle>` and for `bundle:start @<project>`). The command now finds the running bundle from its pid file before it starts anything, and starts nothing. Pickup: restart the framework (`gina framework:restart`) (#B854)
* A bundle that cannot bind its port now ends its boot with exit code 1. When another program held the port (`EADDRINUSE`) or the bind was refused (`EACCES`), the default engine only logged the error and the boot went on: the readiness line `Bundle started !` was printed on its timer and, with nothing listening, the process then exited 0, so `gina-container` exited 0 and the framework read the bundle as started (measured on a booted bundle); on the express engine the error was not handled at all. Until the server listens, a bind error now prints `[ FRAMEWORK ] abort: could not listen on port <port>: <code> (…)` on stderr and the bundle exits 1, and `Bundle started !` is printed only once the server listens. An error the server reports once it listens is handled as before. Pickup: restart the bundle (#B851)
* `gina project:start` no longer overwrites the running framework's pid file or removes its entry from `~/.gina/procs.json`. The command registered itself as the framework: it wrote its own pid into `gina-v<version>.pid`, a helper it ran then removed that file, and its exit removed the framework's `procs.json` entry, while the framework kept running (measured in an isolated daemon). `gina start` checks that entry before it reports the framework as already running. Only the framework's own start registers the framework now; `service:start`, which took the same path (code-read), is changed the same way. Pickup: the next command (#B856)
* After a staged upload is reset, the next file chosen in the same input is posted again. The hidden `<name>[i][…]` inputs that carry a staged file's metadata were built only for the input's first selection; a reset removed them from the form, so the next selection was staged and previewed but the save posted no file, and a later selection with more files than the first got no inputs for the new ones, which the save dropped. The inputs are now built on every selection. The declared `[preview][*]` inputs, and any other `<name>[i][…]` input of the page, that a reset or a delete removes come back, empty, with the next selection, so a form that declares the preview posts the new file's. A page that removes the virtual upload form after a reset, to work around this, keeps working. Browser-bundled: rebuild bundles to pick it up (#B858).
* A reset or a delete now removes a file shown without an image. Both acted only on the `<img>` children of the preview container. A staged file whose staging answer is not an image and carries no `preview` gets no `<img>`, so its reset left its inputs in the form and did not ask the server to remove the staged copy, and the save posted the file the user had removed. In a `<ul>` container, where gina wraps each preview in an `<li>`, the reset did nothing at all. A reset now acts on the input's files. On an edit form, a stored file the page shows without an image is found when its node carries `data-upload-original-filename` naming the file; its delete link was bound to nothing. An `<img>` still works as before. Browser-bundled: rebuild bundles to pick it up (#B859).
* A reset on a multi-file upload input no longer throws, and a delete on an edit form holding several stored files no longer leaves a deleted file in the form. The reset set the input's value to the files still listed, which the browser refuses, so it removed nothing; one delete click removed every preview but only the first file's inputs, sent two removal requests, and the save posted the second file again. Every file of the input is now removed under its own index, in one pass, and the server receives one request naming them all. Any reset or delete control of an input removes all of its files, as before. Browser-bundled: rebuild bundles to pick it up (#B860).
* A staged upload whose preview container has its own id (a `data-gina-form-upload-preview` other than `<input id>-preview`) can be reset again. The reset link's id was derived from the container's, which gave the container's own id: the container was taken for the link, the text `Reset` was written inside it, its classes were changed, and no reset control was bound. The link is now `<input id>-<index>-reset-trigger`, and the reset finds the container the input names. An upload input with no preview container no longer posts empty metadata: reading the missing container threw after the staging answer arrived, before the inputs were filled. Browser-bundled: rebuild bundles to pick it up (#B861).
* A reset now removes the inputs of a staged file whose upload input sets `data-gina-form-upload-prefix`. It removed the inputs named after the input's `name`, so the `<prefix>[i][…]` inputs stayed in the form after the server had been told to remove the staged file, and the save posted a file that was no longer there. Browser-bundled: rebuild bundles to pick it up (#B862).
* A filter, tag or extension a bundle registers through `this.engine` in `controllers/setup.js` (or through `self.engine` in an action) now reaches the templates a custom async swig template loader (`settings.template.swig.loader`) serves. Until now such a template answered 500, with `Invalid filter` (for a tag, `Unexpected tag`) in the server log: the async render path renders through an engine of its own, which never received the bundle's registrations. A bundle filter that has the name of one of gina's own filters (`nl2br`, `getUrl`, …) keeps rendering gina's filter, as it already did for templates on disk (#B825).
* A click on a popin trigger no longer loads the popin twice on a page that holds more than one popin instance. Each `new Popin()` registers a document click proxy that claims the triggers of its own instance by matching their id against its instance id, and that match had no delimiter after the instance id. Instance ids are `gina-popins-` followed by a shared counter (`gina-popins-gp-1`, `gina-popins-gp-14`), so the proxy of `gina-popins-gp-1` also claimed the triggers of `gina-popins-gp-14`, and one click fired both proxies: the popin loaded twice, and the second load replaced the form the first had bound, which then submitted natively. The match now requires the `-` that follows the instance id in every trigger id. Browser-bundled: rebuild your bundles (`gina bundle:build`) to pick it up. (#B876)
### Security
* A request whose urlencoded body, or whose GET/HEAD `inheritedData` query value, carried a bracket-notation field descending into a slot an earlier pair had set to null — for example `a=[null]&a[0][b]=1` — threw inside the request-body parser. On a GET or HEAD that throw had no handler and exited the bundle process, so one unauthenticated request could take a bundle down (an availability defect of the same class as the earlier bracket-nesting crash). The parser now replaces a null slot with a fresh container and nests through it, as it already did a string slot; a number or a boolean slot still ignores the nested field as before. A security advisory accompanies this fix: [GHSA-4992-qqjv-hm4m](https://github.com/gina-io/gina/security/advisories/GHSA-4992-qqjv-hm4m) (#B792).
* In every environment except dev, a route middleware that called one of the controller methods the framework gives it (`self.renderJSON()`, `self.redirect()`, `self.throwError()`, `self.render()`, `self.query()`, `self.getConfig()` and the others) after an `await` or in a callback used the methods of whichever request had last passed through the same middleware file: its answer could be written to another request in flight, and the request it belonged to was never answered. A bundle `controllers/setup.js` had the same defect. Each middleware instance and each `setup.js` run now gets the methods of its own request, and nothing is written onto the middleware class or onto the `setup.js` export. In `setup.js`, `this` is now an object that inherits from the export: read the framework members through `this`, not through the exported function by name, and keep state that must outlive a run elsewhere than on `this`. A security advisory accompanies this fix: [GHSA-hh9m-82xm-hh8h](https://github.com/gina-io/gina/security/advisories/GHSA-hh9m-82xm-hh8h) (#B807).
* The engine-level error responder built its reply from the request held in a Server-wide slot that every incoming request overwrites, so under concurrency an error raised for one request after any asynchronous gap was built from whichever request had arrived last: the wrong JSON-vs-HTML form (an XHR caller could receive the HTML error page, a page request the JSON body), another request's URL, routing and session rendered into the custom error page, a mis-correlated `#ERRREF` log line, and `Access-Control-Allow-Origin` computed from the wrong request's Origin. The responder now resolves the request from the response it is answering, falling back to the previous behaviour only for a non-native response object (#B806). Folded in: an extensionless HTML URL's built-in fallback page is now served with its real `text/html` content type instead of `undefined` (#B815), and a preflight-shaped request that errored before dispatch no longer throws while building the response (it was handed a never-assigned response slot). A security advisory accompanies this fix: [GHSA-cxfq-6655-x4v5](https://github.com/gina-io/gina/security/advisories/GHSA-cxfq-6655-x4v5).
* The context-bearing template filters (`getUrl`, `getWebroot`, `t`, `tIcu`) could resolve another request's context when a template ran on a request path outside a render delegate (#B519, #B809). The filters find their context at call time: a per-render store first, then a process-wide slot that every filter-factory call stamped, every request's render included. A template executed in a controller action through the engine handle (`self.engine.compile(...)(data)`, `compileFile`), with no render store of its own, therefore resolved the context of whichever request had rendered last on the worker: its negotiated culture, and absolute URLs built from that request's host. No concurrency was needed. A scheduled task, a worker or a WebSocket handler rendering with no context of its own read the last request's context the same way. Inside a request the filters now resolve that request's own context: the render store, else the request's own store, on which the controller registers its options. A filter-factory call made inside a request is bound to that request instead of the process-wide slot, which is now read and written only outside a request and so never holds a request's context. The default nunjucks delegate runs its render inside the render store like the other delegates. Affected: every release through 0.7.3. Server-side only: restart the bundle. A security advisory accompanies this fix: [GHSA-7mwq-rqg4-wv2g](https://github.com/gina-io/gina/security/advisories/GHSA-7mwq-rqg4-wv2g).
* A value taken from a request can no longer start a line of its own in the text-format log (CWE-117). The levelled logger used to turn the two written characters backslash + n, r or t inside a logged string into a real control character, and it let a real line feed held by a logged value through, so a logged request value could forge a log line, and escaping it first with JSON.stringify did not help. Now: (1) a written backslash + n, r or t is written as it is; (2) the keys and the string values of a logged object or array, nested arrays included, are written with their control characters as visible escapes — \n, \r, \t, or \uXXXX for the other C0 controls, DEL, the C1 controls and the line separators U+2028 and U+2029; (3) the framework lines that print a request value write it the same way: the multipart upload field names, groups and extensions, the request-body parse warnings, a static file name with an unknown extension, the validator isDate and condition warnings, the route placeholder warning, the template file name lines, the engine.io message lines, the redirect notice, and the error lines of core/server.js, the controller, the context helper and lib/lane, which keep a real line break only before a stack frame or a "caused by:" line; (4) on the isaac engine a query string with no = that is not JSON is reported by its length and the name of the error, at warn, instead of an error stack quoting it. Behaviour changes in the text format: a written backslash + n, r or t no longer breaks the line, so pass a real line feed for a multi-line message; a multi-line string held inside a logged object prints on one line, so pass the Error itself to keep a multi-line stack; an error line writes a line break that no stack frame follows as a visible \n, so a 404 logs "Page not found: \n/path" on one line; the request-body parse warnings print the message of the parser, not its stack; and the upload 400 messages name the field, group or extension with its control characters shown. The JSON format (GINA_LOG_FORMAT=json) still writes one line per message, and its message value follows the same changes. The log redaction now reads a message both as written and with its visible escapes decoded, so a credential next to an escaped control character is masked as it was, and a credential that itself holds a written backslash + n, r or t, printed until now, is masked too. Not changed: a real line feed in a plain string argument still starts a new line, as with Node, and an Error logged by application code keeps its message as it is. Picked up by a bundle restart and a re-bake of the browser bundle (the validator and the routing library changed); the framework daemon and a running gina tail take the logger change at their own restart. (#B830) A security advisory accompanies this fix: [GHSA-mxf4-55c4-3659](https://github.com/gina-io/gina/security/advisories/GHSA-mxf4-55c4-3659).
* A resolved secret that holds a quote is now masked when it is logged inside an object or through `console.log` (CWE-532). The log redaction (#B433) masks every value the secrets resolver substituted for a `${secret:KEY}` placeholder, but the object writers escape the quotes of a string value before the redaction runs: the levelled logger writes a double quote as `\"` and a single quote as `\'`, and the raw `console.log` path renders an object with `JSON.stringify`, which writes a double quote as `\"`. A secret value holding a quote then no longer matched, and it was printed in full in the logged line, on both paths and inside an array logged through `console.log`. The decoded reading of the redaction now reads these two quote escapes too, so the secret is found and masked; as with the control-character escapes of #B830, that reading only adds masks, and nothing else in a log line changes. A secret that holds a backslash, a control character, a lone surrogate or a line break, and the renderers other than the logger's object writer, are covered by the #B838 entry of this release. Pickup: a bundle restart; the logger is not in the browser bundle (#B834). A security advisory accompanies this fix: [GHSA-x9mv-qp85-8mx3](https://github.com/gina-io/gina/security/advisories/GHSA-x9mv-qp85-8mx3).
* A resolved secret is now masked whichever renderer writes it into a log message (CWE-532). The log redaction (#B433) searched a message as the logger's own object writer writes a value. Three other writers alter a value before the redaction runs, and a secret they had altered was printed in full: `JSON.stringify` (an object, an array or an object key logged through `console.log`, or a JSON string the caller built) for a secret that holds a backslash, a control character or a lone surrogate; `util.inspect` (an `Error` that carries the value in one of its own properties, logged at any level or through `console.log`, alone or inside an object) for the same characters, for a long multi-line value, which it splits after each line feed, and for a multi-line value in the message of a nested `Error`, which it indents; and a plain string passed to a level method for a secret that holds a carriage return, which is written as a line feed. The secret values are now searched on every layer of backslash escaping of a message, up to three (a value can be rendered more than once: an `Error` held by an object logged through `console.log`, a JSON string held by an object or by an `Error`), and the line breaks of a secret match the layout those writers give them. Nothing else in a log line changes: the pattern rules read a message as before, and a line that holds no backslash, or only the escapes of the logger's object writer, is searched exactly as before. Not masked: a value that is not written as its own characters (the bytes of a Buffer, base64, URL-encoding, the escapes of another serialiser); a value under more than three layers of escaping; and a secret that sits inside a longer string of more than 10,000 characters held by an `Error`, which `util.inspect` cuts (the head of a secret that is the whole cut string is masked). Pickup: a bundle restart; the logger is not in the browser bundle (#B838).
* A query field named `__proto__` no longer changes the prototype of `req.delete`. On the default engine (isaac), the query parser assigned every field with `request.query[name] = value`, so a `__proto__` field holding a JSON value (`__proto__=%7B%22polluted%22%3A1%7D&a=1`) re-pointed the prototype of the parsed query, and the DELETE branch handed that object over as `req.delete`. On every DELETE to a path after the first (the routing loop copies the bag on a cold route only), a property read such as `req.delete.polluted` returned the injected value while `Object.keys`, `hasOwnProperty` and `JSON.stringify` did not see it, and an injected `count`, `hasOwnProperty` or `toString` made `req.delete.count()`, `req.delete.hasOwnProperty()` or a string conversion throw: a 500 for that request. It stayed within that one request object. Measured on a booted bundle. The parser now drops a field named `__proto__`, `constructor` or `prototype`, as the data helper already did for GET and for bodies (#B592), and the DELETE branch hands over a plain object holding the query's own fields, on every engine. A query field literally named `constructor` or `prototype` no longer reaches `req.delete`, as on GET. Server-side only: restart the bundle, nothing to re-bake (#B848)
* A route placeholder value taken from the request — the query string or body, merged into the request's parameters — was substituted verbatim into a route's `param.file`, `param.path` or `param.namespace` by the router's placeholder fill, AFTER the route requirement had been matched against the URL segment. A request could therefore supply a query value of the same name as a placeholder and override the requirement-validated URL segment, and a value carrying `..` escaped the bundle template root when the template was resolved — an arbitrary template-file read (CWE-22, the CVE-2023-25345 directory-traversal class). The render delegates' own boundary check only inspected the first character of the resolved file, so a `..` in the middle of a filled path passed. The router now fails closed: a request-supplied value that would escape as a path component (a `..` segment, or a leading separator) is rejected before it can fill a filesystem-path parameter, on every rendering engine. Developer-authored static prefixes in `param.file` (which are not request values) are unaffected. (#B833) A security advisory accompanies this fix: [GHSA-3vmh-634f-vwm3](https://github.com/gina-io/gina/security/advisories/GHSA-3vmh-634f-vwm3).
* A page template path that a controller took from the request — passed to `self.setTemplate()`, or written to `req.routing.param.file` in an action — could resolve outside the bundle template root, so a request could read any `.html` file the process can read, rendered through the template engine (CWE-22, the CVE-2023-25345 directory-traversal class). The router's own placeholder fill has been guarded since #B833, but these values reach the swig renderer by other paths: its setTemplate, namespace and `param.path` branches joined the value under the root unchecked, its first-character check let a `..` in the middle of the path through (and, for a path starting with `.`, checked one path but read another, relative to the working directory), and a backslash-separated `..` survived path normalisation and traversed when the file was read, so a handler doing `self.setTemplate('errors/' + req.params.code)` read files outside the root from a `..` or `%5C` URL segment. The nunjucks renderer relied on its loader, whose prefix test accepted a sibling directory whose name starts with the root's (`html2/` next to `html/`). Both renderers now check the path they are about to read and answer 500 when it resolves outside the section's template root (`html` in templates.json); custom error pages are exempt. A bundle that renders templates kept outside that root widens its `html`. (#B867) A security advisory accompanies this fix: [GHSA-42gr-h7r3-mw28](https://github.com/gina-io/gina/security/advisories/GHSA-42gr-h7r3-mw28).
