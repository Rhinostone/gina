## 0.6.13 - 2026-08-22
### Added
* New: a general-purpose key-value primitive (#KV1) — declare namespaces under `settings.json > kv.namespaces` and reach them as `gina.kv('<namespace>')` (or `gina.kv()` for `kv.default`). The handle is promise-native with 13 operations: `get` / `set` / `del` / `has` / `ttl` / `expire` / `setnx` (set-if-absent) / `consume` (atomic read-and-delete — one-shot tokens: the second reader gets null) / `incr` / `decr` (integer counters, TTL on create only) / `delIfEquals` (compare-and-delete, the safe lock-release primitive) / `clear` / `getOrSet` (fetch-or-compute with per-process single-flight). Values are JSON-serialized — null and undefined are refused on every write, a stored null being indistinguishable from a miss; TTLs are milliseconds and must be positive (`ttl: 0` refuses rather than meaning no-expiry). Namespaces are strict-declared: an unknown name throws at the call site instead of silently minting an empty store, and the whole feature is dormant with no `kv` block. Each namespace owns its failure policy (`failMode` `closed`, the default, rejects on backend errors; `open` degrades every operation to its miss-shaped result with a warning). Ships with three backends: in-memory (zero config), redis and SQLite, the latter two selected by pointing a namespace's `store` at a `connectors.json` entry — atomic set-if-absent, consume, compare-and-delete and TTL-on-create-only counters are all server-side, and `GETDEL` is used when the server supports it with a Lua fallback below redis 6.2. Naming a connector that has no kv-store implementation still refuses the boot rather than degrading silently to memory. Deliberately NOT a redis client: no data structures, batch operations, key scanning, binary values, or first-class locks.
* The general-purpose KV primitive (#KV1) gains a redis backend for namespaces shared across hosts: point a namespace's `store` at a `connectors.json` redis entry (`{ "kv": { "namespaces": { "tokens": { "store": "kvRedis" } } } }`) and the namespace is served by redis instead of process memory — so several bundles or replicas can share one namespace, which the in-memory backend cannot do. Every guarantee stays server-side: set-if-absent is a single `SET .. PX .. NX`, consume is `GETDEL` where the server supports it (redis 6.2 and above) and a Lua script below that rather than a `GET` plus `DEL` pair, and compare-and-delete and TTL-on-create-only counters are Lua as well. Keys are prefixed per namespace, so two namespaces may share one connectors entry; cluster keys are deliberately left un-tagged so a namespace spreads across slots, and `clear()` scans each master node. Connection policy — `commandTimeout`, `maxRetriesPerRequest`, `enableOfflineQueue` — is read from the connectors entry and otherwise left at the driver's defaults, so a cache-like namespace can be tuned to fail fast while a token namespace keeps the offline queue. Requires `ioredis` in your project. Naming a connector that has no kv-store implementation still refuses the boot.
* The general-purpose KV primitive (#KV1) gains a SQLite backend — the zero-dependency durable option between in-memory and redis: point a namespace's `store` at a `connectors.json` sqlite entry (`{ "kvDb": { "connector": "sqlite", "file": "/data/kv.db" } }`) and the namespace survives a bundle restart and is visible to any process opening the same file, with no server to run. Namespaces sharing one file are isolated by a composite key rather than a prefix, so `clear()` touches only its own namespace. Every read-modify-write operation — set-if-absent, consume, compare-and-delete, counters — runs inside an IMMEDIATE transaction, so it stays atomic when a SECOND PROCESS shares the file, which is the case the backend exists for. Expiry is filtered on every read and swept periodically, so an expired entry is never observable. Uses `node:sqlite` (built in on Node, a `bun:sqlite` adapter under Bun), so nothing to install. All three backends are now verified against ONE shared contract spec rather than three separate suites.
* Adding an opt-in per-authority circuit breaker to Controller::query() (#MS5, settings.json > server.query.circuitBreaker): after N consecutive transport-class failures to one authority (default 5, each already representing a call whose own retries were exhausted), the circuit opens and every further call fails fast with a machine-readable CIRCUIT_OPEN error (status 503, retryable false, plus the authority and retryAfterMs) instead of hammering a dead upstream; after the cooldown (default 30s) exactly one critical request is admitted as the half-open probe, closing the circuit on success and re-arming it on failure. The gate sits above the HTTP/1.x / HTTP/2 protocol dispatch, so an open circuit rejects before any connection, retry or pre-flight machinery runs and the existing retry invariants are untouched - retries can never hammer an open circuit by construction. Three decisions are load-bearing and documented in-source. Only transport-class errors count: every GinaHttp2Error plus the socket-level ECONN family, checked on err.code and err.cause.code - an application response, whatever its status, flows through the success terminus as data, and a caller bug is neutral, so neither can trip the breaker on a healthy upstream. Only a CRITICAL request may serve as the half-open probe, because a non-critical failure is swallowed by the H3 contract - its callback never fires - so a non-critical probe could never report back and would wedge the half-open state forever. And breaker state lives on the engine instance, the same home as the HTTP/2 session registry, because dev mode re-requires the controller per request: anywhere else the state would reset on every hot-reload, while instance state survives reloads and dies on restart, which is exactly the lifetime circuit state wants. Dormant unless enabled is strictly true; a structurally invalid enabled block refuses the boot rather than warn-and-disable, since silently running without the protection the operator asked for is the fail-open shape the other boot bands refuse. Policy is resolved once at engine start and stamped on the instance, so config changes need a bundle restart. Server-side only, so pickup is a bundle restart with no re-bake
* Documenting two boundaries the framework deliberately does not cross: API versioning and database migrations. Both were absences a reader could only discover by searching for something that was not there, and an absence with no statement behind it reads as an oversight rather than a decision. Neither is a new capability - the point is that neither will be one. Versioning gets a routing-guide section stating plainly that there is no version route field and no version-aware dispatch, because when to cut a version and how long to support the old one are product decisions a framework would be wrong to make for you; it then shows the three shapes the existing primitives already cover, a URL prefix with a per-version namespace so each version loads its own controller file, separate bundles when versions need their own dependencies or release cadence, and header negotiation - with the note that the question deciding between them is not URL versus header but what changes together. Migrations get a models-guide section naming the per-database tools to use instead, plus the two things that actually go wrong in practice: run them as a discrete step before the new version serves, never at bundle boot, where they race themselves the moment there is more than one replica and turn a schema error into a crash-loop instead of a failed deploy step; and keep changes additive during a rolling deploy, because SQL files are validated at call time rather than at boot, so a renamed column and a query still selecting it fail on the first request rather than at startup. The connector CLI page gains an explicit warning that connector:migrate is not a database migration - it lints the connection configuration and with --fix rewrites that JSON, issuing no SQL and holding no up or down concept - since the name is the whole source of the confusion. Verified against the source before writing rather than from memory: no version field exists anywhere in the router or the routing library, and the migrate command help confirms it scans connectors.json only. Docs only, no behaviour change; pickup is a bundle restart with no re-bake
* Identified-caller rate limiting (#MS6): opt-in quota enforcement at the router, keyed on the authenticated principal — the session user (via the operator-named server.rateLimit.keyField) or a machine caller — with fixed-window counters stored in a kv namespace you declare, so a redis- or sqlite-backed namespace shares one quota across replicas while an in-memory one counts per process (the boot resolver warns about the difference, and about a redis connectors entry missing the fail-fast tuning that would otherwise queue requests through an outage). The gate runs after route authorization and before DTO validation (401 -> 429 -> 422), and it throttles identified callers only: anonymous flood control stays with your edge proxy and the HTTP/2 rapid-reset guard, and a request with no resolvable principal is skipped, never bucketed by IP. Denials answer 429 with Retry-After plus the RateLimit / RateLimit-Policy structured fields from draft-ietf-httpapi-ratelimit-headers-11; allowed limited requests carry them too. Per-route overrides ride routing.json's top-level rateLimit key: false exempts a route, an object with limit / window replaces the default policy for that route in its own bucket (partial objects inherit the missing key). Configure under settings.json server.rateLimit (enabled, namespace, keyField, limit, window; env.json keys win at the fold, changes need a bundle restart). Dormant unless enabled is strictly true; structurally invalid values on an enabled block refuse the boot; store outages follow the namespace's own failMode — open admits requests with a warning, closed answers 503 with Retry-After. Server-side only: pickup is a bundle restart (the dist rebuild in this release carries only the route-flag propagation, dead code in the browser).
### Fixed
* Retiring the published claim that gina ships a companion reverse-proxy service (#MS8). The service help text, its JSDoc and the docs-site CLI pages all named `proxy` as one of two framework-internal services you could start, and `gina service:list` reported it with status ok - for a bundle that cannot serve a single proxied request. Measured rather than assumed: the bundle does carry forwarding logic (it reads a Target-URL request header, handles the OPTIONS preflight and pipes an upstream response back), but the HTTP client it calls is never imported and is not a framework global, so any request carrying that header throws a ReferenceError. The internal note claiming the bundle had no proxy logic at all was therefore wrong in its reason while right in its conclusion, and is corrected at source so a later session does not re-derive it. Nothing is being taken away from anyone: the services directory is CLI-generated, gitignored and npmignored, and the published tarball was checked to contain zero entries for it against a firing control, so no release ever carried the bundle the text advertised. The same wording was inaccurate about the other service too - it said these bundles ship alongside gina, which is true of neither - so the sentence now states plainly that services live in a maintainer-side tree outside the published package and that a released install has nothing to list until that tree exists locally. In its place each surface carries the stance: gina ships no edge or reverse proxy by design, run nginx, Traefik or an ingress controller in front of your bundles. That is not a new position, it is the one the rest of the documentation already assumed - the authentication guidance sends OAuth deployments behind a reverse proxy, the rate-limiting roadmap row names your reverse proxy or ingress as the interim answer, and the Kubernetes guide is ingress-fronted throughout - so this aligns four surfaces with one that disagreed. No roadmap row ever promised a built-in proxy, so nothing planned is being cancelled. The dormant bundle is deliberately left on disk: nothing reads it, and deleting generated local state is the operator call. Docs and help text only, no runtime behaviour change; pickup is a bundle restart with no re-bake
* Making the entity dispatch diagnostics readable (#B395). The five DISPATCH markers in the entity callback machinery were raw console.log calls, and in gina that is the logger raw-stdout branch: it bypasses the container dispatch and the level gate alike, so the lines never reached a bundle log file or gina tail, while a daemon-spawned bundle also has its child stdout filtered, so they never reached container logs either. They were diagnostics that could only be seen by running a bundle in the foreground and reading the terminal - which is how a consumer came to report seeing the neighbouring levelled output while these were absent. They now go through console.debug, so they are off by default and appear when the log hierarchy is raised to debug, which was the original intent. The leading newline each line carried is dropped, because it was a formatting hack for the raw stdout path and would otherwise be embedded in the message field under JSON log format, and the prefix now matches the convention already used elsewhere in the same file. The alternative considered was deleting them as spent scaffolding, and it was rejected on measurement rather than on taste: the case for deleting rested on the sites being hot enough that making them visible would flood a debug log, and the full test suite emits fifteen of these lines in total, with two of the four markers never firing at all. Reasoning from the shape of the enclosing handlers is not the same as measuring how often they run. A comment at the first site now records why the method choice is load-bearing, so a later edit does not quietly restore console.log and re-break the visibility. Server-side only, so pickup is a bundle restart with no re-bake
* Fixed #B399 — an exception in a controller's reserved-action hooks (`onReady`, the `setup` controller) could vanish without a response or a visible log line: both dispatch sites invoked the hooks outside the guarded band, so a synchronous throw escaped to the process level (on the built-in engine: uncaughtException killing the whole bundle process; Express answered its own 500 — engine-asymmetric) and an asynchronous rejection was unowned (the request could hang to client/proxy timeout while work after the throw silently never happened). Both hook loops now run inside the dispatch try and every hook's returned promise is owned with the same `.catch` → 500 guard the main action carries, naming the failing hook in the error detail; the synthesized `setup` wrapper now returns the app call's own result so an async `setup.js` rejection reaches the guard. Behaviour change: a rejecting or throwing hook now answers 500 (with the #ERRREF correlation ref) where it previously crashed the process, hung, or let the action's own response mask the failure. The hooks are still dispatched without awaiting, in the same synchronous frame as the action — a hook rejection does not prevent the action from running, so its side effects may already have executed when the 500 reaches the client; treat retries of non-idempotent actions accordingly.
