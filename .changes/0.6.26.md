## 0.6.26 - 2026-09-04
### Fixed
* Error responses no longer crash when the rendered payload carries a non-numeric top-level status (#B466). A page whose own vocabulary includes a field named status - say {status: "draft"} rendered alongside an error - had that value stamped straight into the HTTP response, which threw ERR_HTTP_INVALID_STATUS_CODE and replaced the intended error page with an unhandled 500. The failure was invisible on every successful render and fired only on the error path, i.e. exactly when the error page was needed. Every status the error path resolves is now validated against node's own rule (an integer from 100 to 999) and degrades to a 500 error page when it does not qualify; a numeric status still sets the HTTP status exactly as documented. This also closes the same hole for an explicitly passed three-digit-but-invalid code such as "099", which previously threw as well.
* Error responses now carry the content-type they are meant to declare (#B467). Two branches of the error path - the Internet Explorer override, and the branch taken when a request arrives with no user-agent header at all, which is the common shape for machine callers - passed the header NAME as node's status-message argument instead of passing a headers object. Node therefore read the MIME string character by character: over HTTP/1.1 the response came back with roughly ten to thirty junk headers named 0, 1, 2 and so on, a status line whose reason phrase read content-type, and no content-type header at all; over HTTP/2 the headers were dropped entirely and a status-message warning was emitted. Nothing threw, so the malformed error response was completely silent. Both branches now pass a headers object, matching the two sibling branches beside them, and the plain-text branch declares the bundle encoding as its charset because the error body is JSON written as UTF-8 - a charset-less text/plain invited clients to guess a single-byte encoding and corrupt any non-ASCII text in the error message.
* Staged multipart upload parts stranded by a previous process are now reclaimed at boot (#B469). The `upload.autoTmpCleanupTimeout` deletion timer is per-upload and in-process, so a restart stranded every staged part it was holding, and a part that never reached `self.store()` - a request failing after the multipart parse, or an application consuming the staged file some other way - then had no reclaim path at all: on deployments that restart often, server-generated `.part` files accumulated indefinitely in the configured landing directories. When the timer is armed, server init now sweeps each configured landing directory (the global default plus every group `path`, deduplicated) for staged-shaped `.part` files older than the configured timeout, floored at one hour so an in-flight upload from a sibling live process on a shared staging directory is never touched. The sweep is deliberately conservative: exact server-generated name shape only (a client-named orphan predating the opaque staging names is indistinguishable from an application file and is left alone), regular files only, symlinks never followed, non-recursive. A disabled timer - the shipped default - still arms no sweep: removing staged files then remains the operator's own job, exactly as documented. Applications may also remove `req.files[].path` themselves; the publish path has always tolerated a vanished source, and that tolerance is now a documented contract.
* Job records stranded by a process death are now reclaimed (#B471). The deferred function of an async job lives only in its creating process - a closure cannot be serialised - so a record left `running` (or `pending` past its scheduled retry) by a crash or an unclean restart could never settle: on a durable store its `expiresAt` stayed null forever, the TTL sweep's own guard excluded it, listings reported phantom running work, and the documented polling pattern never terminated. The sweep is now preceded by an orphan-reclaim pass on durable stores: a non-terminal record whose last transition - or whose scheduled retry - is older than `jobs.orphanTimeout` (seconds, default 86400, `0` or `false` disables, floored at 60) is marked `failed` with error name `JobOrphanedError`, after which normal `ttl` retention removes it on schedule. The built-in memory store is exempt, since an in-process store cannot hold another process's orphans; a record reclaimed while its origin was merely slow self-corrects on the origin's next write; and no completion webhook fires for a reclaim - concurrent reclaimers and a self-healing job would otherwise produce contradictory notifications, and the record itself carries the truth.
