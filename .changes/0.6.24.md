## 0.6.24 - 2026-09-02
### Fixed
* Couchbase `bulkInsert` no longer returns `undefined` when its own prologue throws. Its outer `try` wraps the method body, so a synchronous failure — a connection that cannot be resolved, or either of the two deliberate `rec` validations — was caught, logged to `console.error` and then swallowed, and the method fell off the end. Both documented call shapes broke on that path: the `await` form (the first `@example` in its own docblock) resolved with `undefined`, so a caller treating "did not throw" as success recorded an insert that never happened, and the `.onComplete(cb)` form threw a TypeError on `undefined`. In both, the error existed only in the log and was unreachable to the caller. The promise, its one-shot resolver and the `.onComplete` shim are now built before the `try`, so the outer catch settles this call instead: `.onComplete(cb)` receives `(err)` and the promise rejects. The `_settled` latch means a late throw cannot double-settle, and the happy path is unchanged. Note that a fire-and-forget call that ignores the return will now surface an unhandled rejection where it previously failed silently. **Scope, and it matters if you documented the old behaviour:** this changes what `bulkInsert` RETURNS, not what its promise RESOLVES WITH. A rows-less success still settles as `null`, so a non-rejection is still not proof that rows were inserted — keep any rows-based success check you have, and re-read any comment or guard whose premise was the old return-`undefined` behaviour: the premise goes stale while the conclusion usually stays correct. (#B460)
* A Couchbase entity that fails to register now says so, naming itself. `readSource()` guards the whole entity-class construction and `.sql`-derived method attachment under one try, and its catch emitted only a bare stack — while none of its three call sites captures a result or takes an error argument. A throw there therefore left the entity partially built, or absent, with nothing in the log identifying which entity or which `.sql` file was responsible; the first symptom was a missing method at request time, arbitrarily far from the cause. The catch now emits a named diagnostic carrying the entity, the source file, the method being attached and the underlying cause, and still emits the original stack. Boot behaviour is deliberately unchanged: registration failures remain non-fatal, since making an unbuildable entity fatal would stop projects that boot through a swallowed error today. (#B461)
* The Couchbase reconnect classifier no longer throws under every supported SDK. `gina.onError`'s handler tested `err instanceof couchbase.Error`, but no supported couchnode (3.x/4.x) exports a bare `Error` class — verified against a real 4.1.3 `dist/errors.js`, where `Error` is undefined while `CouchbaseError` and 81 sibling classes are present — so the check raised `TypeError: Right-hand side of 'instanceof' is not an object` the moment the handler ran, and because that operand is evaluated first, the shutdown-bucket message arm (which needs no SDK class) was unreachable too. On the Express engine this replaced the real error with the TypeError in subsequent handling; on Isaac the listener is never dispatched at all (middlewares are invoked 3-arg, so the error branch that emits never fires). Each `instanceof` is now guarded on the class existing, in both `connector.v3.js` and `connector.v4.js`. Deliberately NOT an activation: modern SDK errors carry no numeric `.code`, so the guarded arms stay inert, and the SDK-2 shutdown-bucket message greps zero in the 4.1.3 dist. The real error now reaches the handler's designed terminal path instead of being replaced. (#B204)
